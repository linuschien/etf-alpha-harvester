## 1. 系統願景與架構原則 (System Vision & Architectural Principles)

### 1.1 核心設計原則

1. **去常數化（No Magic Numbers）**：所有檔數、門檻與金額皆由「每月投入資本」、「資產總規模」與「標的統計特徵」動態求解，拒絕黑箱與主觀臆測。
2. **規模自適應（Scale-Adaptive）**：從小額資產（月投 1.5 萬 TWD）到高資產規模，系統依交易摩擦自動調節最佳分散程度，兼顧手續費效益與非系統性風險分散。
3. **夏農波動收割（Shannon's Demon Harvesting）**：將市場隨機波動透過動能衛星自適應移動停利與再平衡轉化為確定性的超額報酬（Alpha）；確立「高檔出清整張收割、低檔均線平滑回填核心」之長線閉環。
4. **雲端原生、外部排程與雙軌零維運（Cloud-Native, Scheduler & Dual-Auth）**：
   - 部署於 Google Cloud Platform (GCP) Cloud Run 無伺服器容器平台，徹底解除底層伺服器維護負擔。
   - 系統時間狀態與排程與容器完全解耦，由 **GCP Cloud Scheduler** 於每日 08:00 TST 定時發起 HTTP 請求喚醒服務，徹底解決 Cloud Run 實例歸零（Instance = 0）冷啟動與多實例並行之競爭條件（Race Condition）。
   - 安全邊界實施 **Google Cloud IAP (Identity-Aware Proxy) 與 IAM OIDC Token 雙軌認證共存機制**：人類瀏覽器免密碼登入與排程機器人程式化呼叫各司其職、和諧並存。
5. **小白友善與日常工作流整合（Beginner-Centric & Habit Integration）**：
   - 全面取代使用者手動維護的 Excel 對帳單，提供自動化資產淨值月報與 MoM（月增減）分析。
   - 每日盤後自動比對「自適應移動停利條件」，主動亮燈告警，使用者無需每天登入券商 App 心算。
   - **整張出清、零股留種 (Whole-Lot Harvesting & Odd-Lot Seeding)**：停利時 100% 採整張委託賣出，避開台股盤中零股折價滑價；保留之零股作為種子持續扣款，券商約定合約完全不需更動。
   - **現金流增量自動再平衡 (Cash-Flow Driven Rebalancing)**：停利資金回流單一交割戶，由日常核心大盤之定期定額排程自然、平滑、分批均線吸收，消除手動下達即時買單的操作摩擦與高基期追高風險。
   - 內建「逢低超跌加碼雷達 (Dip-Buying Radar)」，在大盤出現黑天鵝暴跌時引導調用交割戶停利閒置資金進行整張精準撈底。
   - 提供「雙軌庫存與扣款校正機制」，精準克服台股無零碎股機制（以 1 股為單位）所產生的撮合價差。
6. **Clean Code 意圖揭露與資料邏輯分離 (Clean Code & Pure Data Architecture)**：
   - **杜絕晦澀黑話縮寫**：全領域實體欄位全面正名，採用自我意圖揭露（Intention-Revealing）之詞彙（如 `fund_size_twd`、`volume_shares`、`trade_value_twd`、`close_price`、`net_asset_value`、`discount_premium_percentage`、`split_from_shares`、`split_to_shares`、`distribution_frequency`）。
   - **資料歸資料，邏輯歸邏輯**：資料庫嚴格只儲存客觀市場價格與利率事實（如每日行情、FRED 殖利率、分割整數比率），所有衍生狀態（`MacroState`、`CrisisLevel`、`DipBuyingOpportunity`）與建議股債比率均為記憶體中純函數（Pure Functions）運算，絕不在持久層殘留業務狀態。
   - **候選池分組獨立爭鳴**：全域候選池（`CandidateAssetClass`）劃分為 `CORE`、`SATELLITE`、`DEFENSIVE`，各組依專屬多因子模型組內獨立排名（`class_rank`），徹底排除 `ORPHAN`（孤兒標的嚴格專屬於個人持倉層）。
7. **四階段嚴格篩選與正交去共線 (Four-Stage Screening & Orthogonal Pipeline)**：
   - **Stage 0 靜態代碼與合約阻斷**：正則記憶體短路阻斷槓反、期貨、主動型與 ETN，杜絕無效拉取與污染。
   - **資料管線工程基石 (Raw Close & Calendar Days)**：全面強制交易所原始未還原收盤價（Raw Close）與日曆天（365d/90d/30d）標準窗口，杜絕除息動態篡改歷史。
   - **Stage 1 動態數值門禁與池間互斥分流**：歷史長度、動態規模、流動性硬性門禁；核心門禁落選直接除名絕不下放，衛星鎖定高波動與純右側動能。
   - **Stage 2 各資產池多因子連續百分位打分**：Percentile Rank 等權衡配置，產出核心 Top 10、衛星 Top 50、債券 Top 5。
   - **Stage 3 兩兩正交矩陣持久化與通用貪婪正交去共線**：全量計算儲存核心最多 45 組與衛星最多 1,225 組無重複兩兩對稱配對矩陣，以 $R^2 < 0.50$ 標註 `ACCEPTED` 與 `REJECTED_COLLINEAR`，支援預設全局模式 A 與自訂種子錨定模式 B。

### 1.2 系統邊界與 Anti-Goal 宣告

* **IN-SCOPE（系統核心功能）**：
  1. 獨立的市場數據、宏觀利率指標（FRED API）、證交所定期定額排行與新 ETF 採集管線。
  2. 四階段量化篩選、連續百分位評分、兩兩正交矩陣持久化與貪婪正交去共線引擎。
  3. 宏觀三態利率狀態機與危機逆向救災協議。
  4. 個人資本容量自適應求解、極簡庫存帳本與扣款快速微調校正。
  5. 各標的獨立扣款日排程與未來 30 天資金預告日曆。
  6. 先賣後買工單求解器（整股張數 + 盤中零股拆解）、已實現資本利得流水帳。
  7. 除息發放日自動配息入帳（含 76W 海外所得標籤）與單一交割戶可用現金校準。
  8. 月度對帳月報（取代 Excel）、退休 Hurdle Rate、蒙地卡羅財富漏斗錐、雙重報酬（TWR/MWR）與三源歸因。
  9. GCP Cloud Run 容器化部屬、Google Cloud IAP 瀏覽器免密碼驗證與 Cloud Scheduler OIDC 外部排程觸發。
* **OUT-OF-SCOPE / Anti-Goal（嚴格排除事項）**：
  1. 任何短期價格走勢預測、高低點擇時進出（Market Timing）。
  2. 盤中高頻交易、當沖、主觀當日沖銷輔助。
  3. 券商交易 API 直接自動下單（嚴格採用決策輔助工單，由使用者手動在券商 App 委託，零金鑰與交易憑證外洩風險）。
  4. 質押借券凍結股數標記等低頻複雜功能（精簡小白介面）。
  5. 外部離線檔案匯出功能（不產出 PDF/JSON/HTML 檔案，全功能由 Web 儀表板直接互動）。

## 3. 系統全域層功能規格 (Global Domain Services)

### 3.1 模組 G-01：市場數據與情報基石 (Market Data & Intelligence)

本模組為整個系統的客觀基石。由於 Cloud Run 為無狀態無伺服器環境，實例可能縮容至 0，本模組之日常資料採集嚴格由 **GCP Cloud Scheduler 外部排程器** 定時以 OIDC Token 觸發受保護之 HTTP 端點（POST `/api/v1/marketData:sync`）喚醒執行，消除容器內部定時器因實例冷卻休眠或多實例並行造成的競爭條件（Race Condition）。

#### 0. 資料管線工程基石（Data Pipeline Baseline）
* **原始報價真實性原則（Raw Close）**：
  * 所有報酬率、波動度、動能指標及判定係數 $R^2$ 計算，一律強制採用交易所原始未還原收盤價（Raw Close）。
  * 嚴禁在資料庫中引入向前復權（Adjusted Close），避免每次除息動態竄改歷史數據、破壞整數心理價位關卡，並杜絕因除權息事件簿維護延遲造成的系統單點故障（SPOF）。
  * 數理依據：年化 9%~12% 的極端高配息對 $R^2$ 的理論極限影響僅 1.8%~3.2%，在 $R^2 \ge 0.90$ 的硬性門禁下對真核心與高股息的判定具備絕對不變性。
* **全時間維度「日曆天（Calendar Days）」月度自然對齊規範**：
  * Top List 評審以月為週期運作，所有資料時間窗口嚴格以自然月為基準，消弭跨月與跨國休市日不同步之統計歧義：
    - **資料基準截止日**：評審當月上月最後一日（以 9 月為例，資料截止日為 8 月 31 日）。
    - **長期趨勢與回歸視窗（365 日曆天）**：前一年同月 1 日至上月最後一日（以 9 月計算為例，區間為去年 9 月 1 日至今年 8 月 31 日，完整 12 個自然月，嚴格對齊 1 年 365 日曆天）。
    - **中期波動度評估視窗（90 日曆天 / 近一季）**：前 3 個自然月 1 日至上月最後一日（以 9 月計算為例，區間為今年 6 月 1 日至 8 月 31 日，完整 3 個自然月）。
    - **短期流動性評估視窗（30 日曆天 / 近一月）**：上月 1 日至上月最後一日（以 9 月計算為例，區間為今年 8 月 1 日至 8 月 31 日，完整 1 個自然月）。
* **跨時區對齊機制**：
  - 美股資產（S&P 500 `^GSPC`、Nasdaq 100 `^NDX`）：採 Shift 1 天對齊跨時區時差（台股交易日 $T$ 對齊美東 $T-1$ 日）。
  - 日股（日經 225 `^N225`）與台股僅 1 小時時差，採同日曆天直接對齊。
  - 回歸計算：以 365 日曆天內「兩市場皆有開盤交易」之交集日期為準計算 $R^2$（若相關係數 $\rho \le 0$ 強制歸零）。

#### 1. Stage 0：靜態代碼正向表列准入（Pre-fetch 記憶體白名單篩選）
在派發爬蟲任務前，直接由記憶體進行正向表列正規表達式比對，非合格原型標的連 1 筆歷史報價都不予抓取與儲存：
* **准入正規表達式（正向表列）**：`^00\d{2,4}B?$`
* **准入標準（僅允許純原型）**：
  * **純數字標的**（`00\d{2,4}`）：廣基大盤、動能衛星與產業主題之原型股票型 ETF（如 0050、0056、006208、00646、00662、009826 等）。
  * **以 `B` 結尾之標的**（`00\d{2,4}B`）：指數化投資級公債、公司債、金融債等原型債券型 ETF（如 00679B、00720B、00725B、00991B 等）。
* **自動阻斷排除對象（非黑即白，一勞永逸）**：
  * 槓桿/反向型（`L`, `R`，高內耗且不適合長期持有）。
  * 商品期貨型（`U`，轉倉正價差結構性扣血）。
  * 主動管理型（`A`, `D`，主動選股/選債、無客觀追蹤指數、經理人風格漂移風險）。
  * 股債平衡型（`T`，股債比率由經理人動態調配，破壞系統外層資產配置算力）。
  * 加掛外幣/雙幣別（`K`, `C`，如 00668K、00687C，重複掛牌且台幣交割戶無法直接搓合）。
  * 指數投資證券（`02...`，ETN 具券商信用違約風險與到期年限限制）。
  * 任何未來交易所新創之奇異後綴。
* **過濾效益**：全市場 400+ 檔標的經 Stage 0 正向表列篩選後，收斂至約 310~320 檔最高品質的官方純原型 ETF，徹底杜絕雜訊。

* **水位線與自動斷路連動**：

### 3.2 模組 G-02：全域標的治理與多因子排名 (Global Universe & Ranking Engine)

本模組為系統客觀標的治理與多因子評分核心，嚴格落實**「四階段篩選與評分體系 (Stage 0 ~ Stage 3)」**，並依據**「月度排程產出、Watermark 跳過、Admin 歷史覆蓋重算」**之架構運作：

```text
[全市場 250+ 檔 ETF]
        │
        ▼ 【Stage 0：靜態代碼與合約阻斷】(純字串正則比對，0 秒記憶體短路)
[合格原型標的 (約 140~150 檔)]
        │
        ▼ 寫入資料庫日常蓄水，強制採用「原始未還原收盤價 (Raw Close)」動態計算日報酬與 NAV

        │
        ├─ 符合核心門禁 (R^2_TAIEX >= 0.90) ────► 【核心候選池】 (落選直接除名，絕不下放)
        ├─ 符合債券門禁 (代碼 B / 名稱含「債」，排除非投資等級債) ──► 【債券候選池】
        └─ 排除核心/債券且動能正向、高波衝鋒 ────► 【衛星候選池】 (近一季 sigma_90d >= 18% 且 MOM > 0，排除 R^2_TAIEX >= 0.90)
        │

        │

[輸出自然正交清單：標註 ACCEPTED 與 REJECTED_COLLINEAR 衝突來源，落實寧缺勿濫]
```

#### 0. 月度定審排程、Watermark 判定與 Admin 歷史重算規範
1. **每月 1 日月度排程產出機制 (Monthly Cadence on the 1st)**：
   - 產生 Score Top List 嚴格以月為單位（類似每月定期定額概念）。
   - 每月 1 日 08:00 TST（或當月首次排程啟動時），系統以截至上月底之完整歷史月度數據（如 9 月評分採用截至 8 月 31 日之數據）產出當月 Top List。
   - **評審日期標記**：資料庫與 API 統一標記為評審當月 1 號（例如 `evaluation_date = 2026-09-01`，代表「2026 年 9 月號評分榜」）。
   - **定期定額排行對齊**：DCA 定期定額指標直接沿用當下最新已有之期數，不等待月中證交所新月報公告。
2. **Watermark 斷路跳過機制 (Monthly Watermark Bypass)**：
   - 系統利用 `data_feed_sync_watermark` 資料表（`feed_name = 'MONTHLY_TOP_LIST'`）記錄當月 Top List 是否已成功產出。
   - 每日例行排程喚醒時，若比對發現當月 Watermark 記錄已為 `PASS`（已完成當月產出），系統自動**跳過** Top List 與正交矩陣之重複運算，僅執行日常行情同步與守門員檢核。
3. **Admin API 覆蓋與歷史重算機制 (Admin Recalculation Override)**：
   - 管理員可隨時透過受保護端點（`POST /api/v1/globalAssetScores:evaluate?yearMonth=YYYY-MM`）手動觸發評估。
   - **強制覆蓋**：由 Admin API 驅動時，系統自動略過 Watermark 檢查，強制重新運算。
   - **歷史月份重算支援**：Admin 可指定過去特定月份（例如 `yearMonth = "2026-07"`），系統自動截取對應之歷史數據窗口（如去年 7/1 至今年 6/30）重新計算，並完整覆蓋該評審月份之 `GlobalAssetScore` 與 `GlobalAssetPairwiseMatrix`。
4. **半年度個人投組換倉對齊 (Semi-Annual Personal Rebalancing Alignment)**：
   - 個人投組層（P-01, P-02）之 1.4N 緩衝換倉決策，直接以每年 **7 月 1 日**（涵蓋完整上半年 1~6 月數據）與 **1 月 1 日**（涵蓋完整下半年 7~12 月數據）產出之月度 Top List 作為換倉依據。


#### 1. Stage 1：動態數值門禁與池間互斥分流（Daily Quotes 檢驗）
通過 Stage 0 者，後台日常排程自動儲存原始收盤價與 NAV，並在定審時執行動態運算過濾。門禁系統僅執行二元資格審查（Pass / Fail），違者即刻短路淘汰，不予打分：

##### A. 全局通用硬性門禁（三大類別共同遵守，具備絕對物理普適性）
* **歷史資料長度不足**：上市未滿 365 個日曆天（未滿 1 年），或近 365 個日曆天內有效交易日數 $N < 220$ 天 ──► 一票否決。
* **最新資產規模不足**：最新動態規模 $\text{AUM} = \text{發行單位數} \times \text{最新 NAV} < 20 \text{ 億 TWD}$ ──► 一票否決（對接 TWSE MIS 即時淨值與發行單位數計算，防範下市清算風險與造市撤單）。
* **次級市場流動性不足**：近 30 個日曆天日成交金額中位數（Median Daily Turnover）$< 2,000 \text{ 萬 TWD}$ ──► 一票否決（以中位數抵抗特定日極端爆量，防範買賣滑價摩擦，確保造市商穩定掛單深度）。

##### B. 類別專屬分流門禁（嚴格遵循「池間互斥原則」）
* **核心大盤池專屬門禁**：
  * **台灣加權旗艦基準同步性**：與台灣加權指數（`^TWII`）近 365 個日曆天之日報酬判定係數滿足：
    $$R^2_{\text{TAIEX}} < 0.90 \implies \text{一票否決}$$
    （此處 $R^2$ 採用近 365 日曆天有效開盤交易日之日報酬計算；若相關係數 $\rho \le 0$ 則強制歸零）。
  * **池間互斥鐵律**：通過此門禁之標的，僅代表具備「核心長線財富水庫」資格；若在核心組評分競賽中落選，直接除名淘汰，絕不下放衛星池。
* **防衛債券池專屬門禁**：
  * 代碼以 `B` 結尾或標的名稱包含「債」。
  * **非投資等級債（High Yield）一票否決**：標的名稱或追蹤指數包含「非投資等級」、「非投等」、「高收益」或「High Yield」者 ──► 一票否決（嚴格維持防衛水庫之高信用評等避險屬性，避免在流動性危機時承擔信用違約風險）。
  * 實質年化殖利率客觀評估：維持 Trailing 1-Year 現金殖利率客觀評估。
* **動能衛星池專屬門禁**：
  * **非核心股票屬性**：排除核心大盤標的（$R^2_{\text{TAIEX}} \ge 0.90$）與債券標的。
  * **近一季波動能量硬性門禁**：近 90 個日曆天（近一季）年化波動度 $\sigma_{90d} < 18\%$ ──► 一票否決（年化波動度 $\sigma_{90d} = \text{該 90 日曆天窗口內有效日報酬標準差} \times \sqrt{252}$；低波動高股息標的因 $\sigma$ 常態落在 11%~14%，在此關卡直接被秒殺超渡）。
  * **純右側動能一票否決**：$\text{MOM}(12\text{M}) \le 0$ ──► 一票否決（以近 365 日曆天累積報酬衡量，杜絕接刀特定下行產業的價值陷阱，確保資金全速推動夏農收割飛輪）。

#### 2. Stage 2：各資產池多因子連續打分（Scoring & Ranking）
通過門禁分流後，標的在其所屬賽道內進行名次導向之連續變數百分位數（Percentile Rank, 0 ~ 1）打分排序，避免極端數值扭曲權重。各池主力因子均採等權重均衡配置，無淘汰邏輯，只決定名次先後：

| 資產池類別 | 多因子打分公式 | 輸出進入 Stage 3 規格 |
|---|---|---|
| **核心大盤 (Core)** | $S_{\text{core}} = \frac{1}{3}\text{Rank}(R^2_{\text{TAIEX}}) + \frac{1}{3}\text{Rank}(\text{DCA}) + \frac{1}{3}\text{Rank}(\text{AUM})$ | 取前 10 名進入「核心 Top 10」 |
| **動能衛星 (Sat)** | $S_{\text{sat}} = \left( \frac{1}{3}\text{Rank}(\text{MOM}) + \frac{1}{3}\text{Rank}(\text{KER}) + \frac{1}{3}\text{Rank}(\text{Sharpe}) \right) \times (1 - R^2_{\text{TAIEX}})$ | 取前 50 名進入「衛星 Top 50」 |
| **防衛債券 (Bond)** | $S_{\text{bond}} = 0.70 \times \text{Rank}(\text{YTM}) + 0.30 \times \text{Rank}(\text{AUM})$ | 取前 5 名進入「債券 Top 5」 |

##### 子因子定義與計算規則：
1. **核心大盤池評分（追蹤純度與資金共識，各佔 1/3）**：
   * $\text{Rank}(R^2_{\text{TAIEX}})$（佔 1/3）：與台灣加權指數（`^TWII`）近 365 個日曆天的判定係數百分位。
   * $\text{Rank}(\text{DCA})$（佔 1/3）：證交所每月定期定額交易戶數百分位（維持現有精確實作，定期定額 Top 20 標的皆具備正向得分，第 1 名 1.0、第 20 名 > 0，榜外標的戶數為 0，得分 0.0）。
   * $\text{Rank}(\text{AUM})$（佔 1/3）：最新資產規模百分位（衡量長期降費潛力與造市深度）。
2. **動能衛星池評分（純粹 Alpha、平滑路徑與正交去影子，動能三因子各佔 1/3）**：
   * $\text{Rank}(\text{MOM})$（12-1 月經典動能，佔 1/3）：$\text{MOM}(12-1) = [P(T - 30\text{d}) / P(T - 365\text{d})] - 1$，取過去 365 個日曆天累積報酬並剔除近 30 個日曆天短線走勢之百分位。
   * $\text{Rank}(\text{KER})$（365 個日曆天考夫曼效率比，佔 1/3）：$\text{KER} = \frac{|\text{淨位移}|}{\text{總路徑長度}} = \frac{|P(t) - P(t-365\text{d})|}{\sum_{i} |P(i) - P(i-1)|}$ 之百分位，衡量價格推進的平滑度。
   * $\text{Rank}(\text{Sharpe})$（近 365 個日曆天純夏普值，佔 1/3）：$\text{Sharpe} = \frac{\text{Mean}(r)}{\text{Std}(r)} \times \sqrt{252}$（不扣除無風險利率，$r_f = 0$）之百分位。

3. **防衛債券池評分（鎖定實質現金流與機構深度）**：
   * $\text{Rank}(\text{YTM})$（實質年化現金殖利率，佔 70%）：Trailing 1-Year Cash Dividend Yield 百分位。
   * $\text{Rank}(\text{AUM})$（資產規模，佔 30%）：確保在信用流動性緊縮時具備二級市場造市深度。
   * 防衛債券組直接由 Rank 1 標的入選最終投組配置，不進行 Stage 3 正交去共線。

#### 3. Stage 3：兩兩正交矩陣持久化與通用貪婪正交去共線演算法 (Stage 3 Orthogonal Engine)
本模組徹底拔除固定參數 $k$ 限制，改採全量掃描標示機制，並支援人機協同決策之「雙模式錨定重算」。核心池（Top 10）與衛星池（Top 50）共用同一運算引擎：

##### 1. 兩兩正交矩陣持久化 (Pairwise Matrix Persistence)
* 系統對 Stage 2 產出之清單執行全量兩兩日報酬判定係數 $R^2$ 與相關係數 $\rho$ 運算，並持久化保存至 `global_asset_pairwise_matrix` 資料表：
  - **核心大盤池**：最多 $10 \times 9 / 2 = 45$ 組無重複兩兩對稱配對。
  - **動能衛星池**：最多 $50 \times 49 / 2 = 1,225$ 組無重複兩兩對稱配對。
* 持久化矩陣支援前端雷達快速查詢任意兩檔標的之共線程度，無需反覆即時重算。

##### 2. 數理正交判定標準
* **互斥門檻**：兩兩標的近 365 個日曆天之原始日報酬判定係數必須滿足：
  $$R^2(\text{Candidate}, \text{Selected}) < 0.50$$
  （等價於高維幾何空間夾角 $\theta > 45$ 度；皮爾森相關係數 $\rho \le 0$ 時自動歸零安全放行）。

##### 3. 雙運算模式支援
* **模式 A（預設全局正交）**：
  * **起點**：自動鎖定 Stage 2 綜合評分 Rank 1 標的為初始種子（Seed），標記為 `ACCEPTED` 加入已選集合 $\mathcal{S} = \{\text{Rank 1}\}$。
  * **遍歷**：由 Rank 2 依序向下審查至名單末端。若當前候選標的與 $\mathcal{S}$ 中「所有已選標的」之 $R^2$ 均 $< 0.50$，則標記為 `ACCEPTED` 並加入 $\mathcal{S}$；若與 $\mathcal{S}$ 中任一標的 $R^2 \ge 0.50$，則標記為 `REJECTED_COLLINEAR`，並記錄衝突來源。
* **模式 B（自訂種子錨定）**：
  * **起點**：使用者因個人偏好（如已持有特定部位），可自 Stage 2 的 Top 清單中指定任一標的 S 為錨定種子。
  * **強制置頂**：種子 S 優先入選，標記為 `ACCEPTED` 成為初始已選集合 $\mathcal{S} = \{S\}$。
  * **遍歷**：清單中其餘標的嚴格按照 Stage 2 原評分由高至低依序審查，逐一比對與 $\mathcal{S}$ 中標的之正交條件。

##### 4. 全量標註輸出與自然飽和終止
* **全量遍歷標示**：名單內每一檔標的均被標註明確狀態與衝突資訊：
  - `ACCEPTED`：正交入選標的。
  - `REJECTED_COLLINEAR`：共線衝突排除，並詳細記錄衝突來源（例如 `Collinear with 00757 (R^2 = 0.71)`）。
* **飽和自然終止**：若向下審查無任何標的能與已選集合滿足正交條件，演算法自然結束，嚴禁為了湊滿特定檔數而調寬門檻，落實「寧缺勿濫」之極致量化紀律。
* **核心豁免與評分表純淨原則**：
  - 核心大盤標的永久禁止產生任何主動清倉指令，僅接受資金流入與再平衡補償。
  - `global_asset_score` 僅儲存通過 Stage 1 門禁之合格候選標的，記錄 Stage 2 各子因子得分、綜合得分與組內名次（`class_rank`），以及 Stage 3 模式 A 之正交狀態與衝突來源。未通過 Stage 1 門禁者於日誌留痕，不寫入評分表。

* **免每月改定額**：日常由券商自動扣款，系統不頻繁調整約定定額；約定額度僅在**每半年審核 (6/30, 12/31)** 時重算推薦一次。
* **現金流增量自動再平衡 (Cash-Flow Driven Inflow Rebalancing - 預設主軌道)**：
  * 停利賣出整張所釋出的大額現金（本金 ＋ 利潤），於交割後回流至單一交割戶 (`Free Cash`)。
  * **核心哲學（均線回填免手動買單）**：系統**不強制要求使用者在停利當日手動下單即時買進核心**（避免大多頭高檔追高接刀與兩段式下單摩擦）。該筆閒置資金作為「定期定額燃料庫」，由原本約定好的核心大盤與防禦債券之定期定額排程（如 6, 16, 26 號）在未來數月內**平滑、分批、自動於均線均價買入核心**，達成真正優雅的夏農波動收割閉環。
* **低頻單筆工單觸發例外 (Manual Rebalancing Exceptions)**：
  1. 孤兒標的 (ORPHAN) 汰換清倉且釋出大額現金；
  2. 標的權重偏離目標超出容忍帶 $\vert{}\frac{W_{\text{actual}} - W^*}{W^*}\vert{} \ge 25\%$；
  3. 「逢低超跌加碼雷達」亮燈確認手動加碼。

#### 5. 先賣後買工單求解器與已實現資本利得記錄
* **先賣後買原則**：工單排序嚴格遵守「先出清 ORPHAN 與衛星停利賣單 $\to$ 確認交割款 $\to$ (若有) 執行買單」，杜絕違約交割。
* **整零股委託最佳化**：
  * **衛星停利單**：100% 嚴格為「整張委託（$\lfloor Q/1000 \rfloor$ 張）」，永不產生零股賣單。
  * **ORPHAN 出清單**：整張出清 ＋ 零股結清（徹底清空被淘汰標的）。
  * **超跌加碼買單**：優先建議「整張買進（1 張）」，免除零股撮合困擾。
* **已實現資本利得入帳**：
  * 使用者點擊「確認賣出成交」後，系統依加權平均成本自動結算：
    $$\text{已實現資本利得} = (\text{成交單價} - \text{買入均價}) \times \text{賣出股數} - \text{手續費} - \text{證券交易稅 (0.1\%)}$$
  * 寫入 `TradeTransaction` 交易流水帳，並自動累計至當月/年度已實現損益統計。

#### 6. 三大極簡 What-If 壓力沙盤推演
系統提供無副作用的虛擬推演：
* **劇本 A（大盤常態回撤 -10%）**：試算哪些衛星會觸發移動停利、核心大盤產生的權重缺口。
* **劇本 B（黑天鵝暴跌 -30%）**：預演防禦債券套現 50% 抄底核心大盤的確切股數與金額。
* **劇本 C（降息 100bps/景氣衰退）**：預演公司債 YTM 跌破 3.5% 觸發債券停利釋放的資本利得規模。

### 4.3 模組 P-03：個人現金水位、扣款預告與配息 (Personal Cash & Dividends)

#### 1. 極簡單一交割戶可用現金校準 (Free Cash Calibration)
* 使用者每月只需在介面輸入一個數字：「**交割戶當前可用現金餘額**」，系統直接以此作為當前可支配資金，無需繁複逐筆記帳。

#### 2. 本月扣款排程與交割資金預告日曆 (DCA Cash Forecast)
* 系統根據各標的設定的 `dca_days` 與約定扣款金額，自動生成未來 30 天資金日曆：
  * *「6 號預計扣款 0050 $5,000、16 號預計扣款 00646 $3,000，累計需準備 $8,000，目前交割戶餘額充足 / 尚缺 $1,500」*，及早預警補足存款。
* **停利資金充裕度與免入金月數試算 (DCA Runway from Harvested Cash)**：
  * 當停利釋出大額現金入帳後，系統動態推算現金可支撐之月數：
    $$\text{DCA Runway (Months)} = \frac{\text{Free Cash}}{C_{\text{monthly}}}$$
  * 戰情室即時顯示醒目激勵資訊：*「【交割戶充裕】目前可用現金 $96,000，未來 3.8 個月定期定額已完全由停利資金覆蓋，無需額外自薪資帳戶入金！」*，極大化小白投資人的心理安全感與被動投資正反饋。

#### 3. 已實現配息自動入帳 (Realized Dividend Ledger)
* 在公開除息發放日（Payment Date）當天，系統自動根據使用者在除息基準日（Ex-Date）持有的庫存股數 $Q$ 與每股股利 $D$ 自動計算入帳：
  $$\text{已實現配息金額} = Q \times D$$
* 自動標註 `76W`（海外利息所得）免稅額標籤（針對 00720B 等海外債 ETF）。
* 寫入 `DividendTransaction` 帳本，計入「年度累積領息總額」統計。

### 4.4 模組 P-04：個人月度對帳月報、退休導航與歸因 (Personal Hurdle & Ledger)

#### 1. 月度資產對帳月報 (全面取代 Excel 檔案)
* 每月自動生成資產淨值快照（股票現值 + 債券現值 + 現金）。
* 自動拆解當月淨值月增減金額 ($\Delta V$) 與月增減率 (MoM %)：
  $$\Delta V_{\text{total}} = \underbrace{\Delta C_{\text{savings}}}_{\text{本月新儲蓄注資}} + \underbrace{\Delta P_{\text{market}}}_{\text{市場資本利得/未實現損益}} + \underbrace{D_{\text{dividends}}}_{\text{已實現配息入帳}}$$
* 繪製個人長線資產累積走勢圖，徹底省去每個月開啟 Excel 鍵入對帳單的痛點。

#### 2. 退休目標 Hurdle Rate 與蒙地卡羅財富漏斗錐 (Cone of Wealth)
* **由上而下求解**：輸入退休剩餘年限 $T$、目前總資產 $V_0$ 與預期退休金終值 $V_{\text{target}}$，求解達標所需之最低實質年化報酬率 $r_{\text{req}}$。
* **蒙地卡羅推演**：模擬 10,000 次路徑，建立 $P_{10} \sim P_{90}$ 財富漏斗錐。
* **航道偏離狀態機 (Trajectory State)**：
  * `AHEAD` ($\text{Gap} \ge +20\%$)：超前預期，提示獲利鎖定。
  * `ON_TRACK` ($-10\% \le \text{Gap} < +20\%$)：維持紀律，無須調整。
  * `LAGGING` ($-25\% \le \text{Gap} < -10\%$)：計算需額外補貼之月儲蓄額 $\Delta C$。
  * `CRITICAL` ($\text{Gap} < -25\%$ 連續 2 季)：觸發策略重審會話，建議延後退休或調降終值。

#### 3. 雙重績效度量與三源績效歸因
* **Unitized TWR**：單元化時間加權報酬率，排除存提款干擾，對標大盤 Benchmark。
* **MWR / XIRR**：資金加權報酬率，真實反映個人帳戶年化複合成長率。
* **三源歸因模型**：
  $$\text{Total Return} = \beta \cdot R_{\text{market}} + \alpha_{\text{shannon}} + R_{\text{carry}}$$
  * 每日同步運算「靜態買入死抱到底 (Buy & Hold)」對照組，證明夏農收割超額 $\alpha_{\text{shannon}}$ 的真實價值。

## 5. 雲端平台、安全規範與非功能性需求 (Cloud Platform & NFR)

### 5.1 GCP 雲端伺服器無狀態架構與安全規範 (Cloud Run, Scheduler & Dual-Ingress Security)

#### 5.1.1 容器化微服務與無狀態部署 (Stateless Containerization)
* **單一全功能映像檔**：前端採用 React + Vite 現代化 SPA 儀表板，後端採用高效能 API 服務 (Spring Boot 3.x / Java 25)，封裝為單一極致輕量 Docker 容器。
* **無伺服器彈性縮放 (Serverless Auto-Scaling)**：
  * 平常無連線訪問時，Cloud Run 自動將容器實例縮容至零（Scale to 0），達成真正的免維運與極致雲端節費。
  * 任何外部請求進入時，自動觸發冷啟動（Cold Start）提供服務。

#### 5.1.2 外部排程喚醒架構 (External Cloud Scheduler Orchestration)
* **痛點消除（解決實例為 0 與多實例競爭）**：
  * 在 Cloud Run 容器內部執行常駐定時器（如 `@Scheduled` 或 Linux Cron）存在兩大致命缺陷：(1) 實例縮容至 0 時定時器直接停擺；(2) 流量高峰觸發多實例並行擴展時，多個容器同時執行排程將造成嚴重的資料重複拉取與寫入競爭（Race Condition）。
  * 系統採取「**排程邏輯與運算執行完全解耦**」原則：容器內部不維護常態性時間定時器，改由 **GCP Cloud Scheduler** 承擔外部統一排程器角色。
* **觸發機制與排程配置**：
  * 頻率：每日台北時間 08:00 (UTC 00:00，Cron: `0 0 * * 1-5`)。
  * 目標端點：`POST https://<CLOUD_RUN_SERVICE_URL>/api/v1/marketData:sync`。
  * 任務職責：喚醒 Cloud Run 單一實例，依序執行 G-01 市場資料拉取、守門員檢核、G-02 多因子評估與 G-03 宏觀利率狀態機更新。

#### 5.1.3 雙軌身分認證閘門架構 (Dual-Ingress Authentication: IAP & OIDC Coexistence)
打破傳統「IAP 網頁驗證與 IAM 服務叫用只能二選一」的迷思，系統建構業界標準的**雙軌身份共存架構**：

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        雙軌流量進入閘門 (IAP & OIDC Ingress Architecture)               │
├────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                        │
│  【人類使用者通道：Web 瀏覽器】                                                         │
│   使用者發起請求 (GET /)                                                               │
│          │                                                                             │
│          ▼                                                                             │
│  ┌──────────────────────────────────────────────┐                                      │
│  │ Google Cloud IAP (Identity-Aware Proxy) 邊界 │ ◄── 轉址 Google OAuth 網頁登入         │
│  └──────────────────────┬───────────────────────┘     檢查 roles/iap.httpsResourceAccessor │
│                         │ 通過驗證                                                      │
│                         ▼ 注入 Header: X-Goog-Authenticated-User-Email                 │
│  ┌──────────────────────────────────────────────────────────────────────────────────┐  │
│  │ Cloud Run 容器應用程式 (Spring Boot)                                              │  │
│  │  - 個人投組層 (P-01 ~ P-04)：依 User Email 嚴格隔離多租戶個人資產帳本            │  │
│  └──────────────────────────────────────────────────────────────────────────────────┘  │
│                         ▲                                                              │
│                         │ 通過驗證                                                      │
│  ┌──────────────────────┴───────────────────────┐                                      │
│  │ Google Cloud IAP (Identity-Aware Proxy) 邊界 │ ◄── 驗證 OIDC Bearer Token            │
│  └──────────────────────────────────────────────┘     Audience = IAP OAuth Client ID   │
│          ▲                                            檢查 roles/iap.httpsResourceAccessor │
│          │ 攜帶 OIDC ID Token (由專屬 Service Account 簽署)                            │
│  【自動排程通道：GCP Cloud Scheduler】                                                 │
│   每日定時觸發 POST /api/v1/marketData:sync                                            │
│                                                                                        │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

* **軌道一：人類 Web 使用者通道 (End-User Browser Channel)**：
  1. 存取點：瀏覽器存取 Cloud Run 服務網址或綁定網域。
  2. 認證流程：由 Google Cloud IAP 自動攔截未登入連線，導向 Google OAuth 登入介面，強制檢查使用者是否具備 `roles/iap.httpsResourceAccessor` 存取授權。
  3. 帳本隔離：IAP 驗證放行後，自動向後端注入 `X-Goog-Authenticated-User-Email` 與 `X-Goog-IAP-JWT-Assertion` Header。後端個人投組層（P-01 ~ P-04）以此 Email 作為唯一租戶 Key，達成多租戶資產與庫存的物理級數據隔離。
* **軌道二：自動化排程機器人通道 (Cloud Scheduler Service Account Channel)**：
  1. 存取點：Cloud Scheduler HTTP Target，指向 `/api/v1/marketData:sync`。
  2. 專屬身分：指派專用 Service Account（如 `alpha-harvester-scheduler@${PROJECT_ID}.iam.gserviceaccount.com`）。
  3. **Audience 規格規範（防 401 關鍵約束）**：
     * 啟動 IAP 後，Cloud Scheduler 的 `--oidc-token-audience` **必須嚴格填入該 IAP 背後綁定的「OAuth 2.0 Client ID」**（格式為 `*.apps.googleusercontent.com`），而非 Cloud Run 服務網址！
  4. **IAM 雙重授權綁定**：該 Service Account 必須同時被授予：
     * `roles/run.invoker`（Cloud Run 叫用權限）
     * `roles/iap.httpsResourceAccessor`（穿越 IAP 閘道存取權限）

#### 5.1.4 應用層深度防禦 (Application-Level Defense-in-Depth)
* **維運排程端點防護**：
  * 後端在 `/api/v1/jobs/**` 路由實施二次權限白名單過濾。
  * 即使一般合法使用者登入 IAP，若其 Email 不在核准的 Scheduler Service Account 清單內，後端直接拒絕並回傳 `403 Forbidden`，防止一般終端使用者惡意或誤觸重度數據採集管線。

#### 5.1.5 持久化儲存與資料分區 (Persistence & Tenant Isolation)
* **雲端資料庫**：採用雲端託管關聯式資料庫 (Cloud SQL PostgreSQL / SQLite 雲端持久掛載)。
* **全域 vs 個人分區**：
  * 全域市場行情與宏觀狀態資料表為全系統共享，不帶租戶 ID。
  * 所有個人持倉、扣款日曆、交易流水與對帳月報均以 `user_email` 進行嚴格外鍵約束與索引分區。

### 5.2 介面體驗與小白友善規格 (Beginner-Friendly UX)
* **四步月度引導流程**：
  1. *查看市場與宏觀狀態*（系統自動顯示高利蓄水/常態平衡等綠燈）。
  2. *輸入交割戶可用現金*（小白每月只要填一個數字）。
  3. *查看工單建議*（清楚標示整股幾張、零股幾股、預估成交金額）。
  4. *下單完成後一鍵確認*。
* **全平台 Web 介面響應式設計**：支援桌面瀏覽器與手機瀏覽器自適應呈現。
* **零外部檔案依賴**：不提供 PDF/JSON 匯出，所有數據與圖表即時於線上戰情室渲染。
