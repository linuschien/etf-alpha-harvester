## 1. 系統願景與架構原則 (System Vision & Architectural Principles)

### 1.1 核心設計原則

1. **去常數化（No Magic Numbers）**：所有檔數、門檻與金額皆由「每月投入資本」、「資產總規模」與「標的統計特徵」動態求解，拒絕黑箱與主觀臆測。
2. **規模自適應（Scale-Adaptive）**：從小額資產（月投 1.5 萬 TWD）到高資產規模，系統依交易摩擦自動調節最佳分散程度，兼顧手續費效益與非系統性風險分散。
3. **夏農波動收割（Shannon's Demon Harvesting）**：將市場隨機波動透過動能衛星自適應移動停利與再平衡轉化為確定性的超額報酬（Alpha）；確立「高檔出清整張收割、低檔均線平滑回填核心」之長線閉環。
4. **雲端原生、外部排程與雙軌零維運（Cloud-Native, Scheduler & Dual-Auth）**：
   - 部署於 Google Cloud Platform (GCP) Cloud Run 無伺服器容器平台，徹底解除底層伺服器維護負擔。
   - 系統時間狀態與排程與容器完全解耦，由 **GCP Cloud Scheduler** 於每日 08:00 TST 定時發起 HTTP 請求喚醒服務，徹底解決 Cloud Run 實例歸零（Instance = 0）冷啟動與多實例並行之競爭條件（Race Condition）。
   - 安全邊界實施 **Google Cloud IAP (Identity-Aware Proxy) 與 IAM OIDC Token 雙軌認證共存機制**：人類瀏覽器免密碼登入與排程機器人程式化呼叫各司其職、和諧並存。
5. **小白友善與日常工作流整合（Beginner-Centric & Habit Integration）**：
   - 全面取代使用者手動維護的 Excel 對帳單，提供自動化資產淨值月報與 MoM（月增減）分析。
   - 每日盤後自動比對「自適應移動停利條件」，主動亮燈告警，使用者無需每天登入券商 App 心算。
   - **整張出清、零股留種 (Whole-Lot Harvesting & Odd-Lot Seeding)**：停利時 100% 採整張委託賣出，避開台股盤中零股折價滑價；保留之零股作為種子持續扣款，券商約定合約完全不需更動。
   - **現金流增量自動再平衡 (Cash-Flow Driven Rebalancing)**：停利資金回流單一交割戶，由日常核心大盤之定期定額排程自然、平滑、分批均線吸收，消除手動下達即時買單的操作摩擦與高基期追高風險。
   - 內建「逢低超跌加碼雷達 (Dip-Buying Radar)」，在大盤出現黑天鵝暴跌時引導調用交割戶停利閒置資金進行整張精準撈底。
   - 提供「雙軌庫存與扣款校正機制」，精準克服台股無零碎股機制（以 1 股為單位）所產生的撮合價差。

### 1.2 系統邊界與 Anti-Goal 宣告

* **IN-SCOPE（系統核心功能）**：
  1. 獨立的市場數據、宏觀利率指標（FRED API）、證交所定期定額排行與新 ETF 採集管線。
  2. 全市場多因子量化評分與 1.4N 安全緩衝汰換機制。
  3. 宏觀三態利率狀態機與危機逆向救災協議。
  4. 個人資本容量自適應求解、極簡庫存帳本與扣款快速微調校正。
  5. 各標的獨立扣款日排程與未來 30 天資金預告日曆。
  6. 先賣後買工單求解器（整股張數 + 盤中零股拆解）、已實現資本利得流水帳。
  7. 除息發放日自動配息入帳（含 76W 海外所得標籤）與單一交割戶可用現金校準。
  8. 月度對帳月報（取代 Excel）、退休 Hurdle Rate、蒙地卡羅財富漏斗錐、雙重報酬（TWR/MWR）與三源歸因。
  9. GCP Cloud Run 容器化部屬、Google Cloud IAP 瀏覽器免密碼驗證與 Cloud Scheduler OIDC 外部排程觸發。
* **OUT-OF-SCOPE / Anti-Goal（嚴格排除事項）**：
  1. 任何短期價格走勢預測、高低點擇時進出（Market Timing）。
  2. 盤中高頻交易、當沖、主觀當日沖銷輔助。
  3. 券商交易 API 直接自動下單（嚴格採用決策輔助工單，由使用者手動在券商 App 委託，零金鑰與交易憑證外洩風險）。
  4. 質押借券凍結股數標記等低頻複雜功能（精簡小白介面）。
  5. 外部離線檔案匯出功能（不產出 PDF/JSON/HTML 檔案，全功能由 Web 儀表板直接互動）。

## 3. 系統全域層功能規格 (Global Domain Services)

### 3.1 模組 G-01：市場數據與情報基石 (Market Data & Intelligence)

本模組為整個系統的客觀基石。由於 Cloud Run 為無狀態無伺服器環境，實例可能縮容至 0，本模組之日常資料採集嚴格由 **GCP Cloud Scheduler 外部排程器** 定時以 OIDC Token 觸發受保護之 HTTP 端點（POST `/api/v1/jobs/sync-market-data`）喚醒執行，消除容器內部定時器因實例冷卻休眠或多實例並行造成的競爭條件（Race Condition）。

#### 1. 資料源整合
* **台股 ETF 與全球五大市場基準指數日行情**：每日台北時間 08:00 (UTC 00:00，Cron: `0 0 * * *`) 由 Cloud Scheduler 觸發統一數據採集作業，自動從臺灣證券交易所 (TWSE)、櫃買中心 (TPEx) OpenAPI、Yahoo Finance 與美國財政部統一拉取前一交易日全球收盤行情，強制同步拉取全球五大市場基準指數：
  1. `^TWII`：台灣發行量加權股價指數 (台股總體 Beta 基準、回撤監控線)
  2. `^GSPC`：美國標普 500 指數 (美股廣基 Beta 基準)
  3. `^NDX`：美國那斯達克 100 指數 (全球頂尖科技與動能衛星基準)
  4. `^SOX`：美國費城半導體指數 (晶片與硬體科技領先循環基準，對標 00830)
  5. `^N225`：日本日經 225 指數 (亞洲成熟市場對標、日圓利差交易風險風向球)
* **美國宏觀利率**：每日定時向 Federal Reserve Economic Data (FRED) API 拉取：
  * 美國投資級公司債到期殖利率 (ICE BofA US Corporate Index Effective Yield, 代碼 `BAMLC0A0CM`)。
  * 10 年期美國公債實質殖利率 (`DGS10`) 與 20 年期殖利率 (`DGS20`)。
* **證交所定期定額排行榜**：每月 15 日前定時拉取證交所公告之「定期定額交易戶數 Top 20 ETF 標的與戶數」。
* **新上市 ETF 與基本面**：自動比對掛牌清單，維護掛牌日期、追蹤指數、發行投信、最新總費用率 (TER) 與資產規模 (AUM)；定時拉取各 ETF 的公開除息日程（除息日 Ex-Date、發放日 Payment Date、每股現金股利 $D$）。
* **外部接口技術規格書 (External Specs)**：所有外部資料源（TWSE/TPEx OpenAPI、TWSE MIS、Yahoo Finance、FRED）之連線端點、即時驗證範例與欄位轉換契約，請嚴格參見 [External Interface Specifications](../external-specs/README.md)。

#### 2. 數據齊備性守門員 (Data Completeness Gatekeeper)
* 在每天盤後執行下游因子運算前，守門員自動執行檢核：
  $$\text{Completeness Check} = \begin{cases} \text{PASS}, & \text{所有監控標的均有當日有效收盤價且 FRED YTM 最新數值正常} \\ \text{HALT}, & \text{缺失關鍵收盤價或數值異常偏離 } (> 20\% \text{ 瞬間脈衝跳空}) \end{cases}$$
* 若未通過，發送系統告警並暫停下游自動狀態更新，防止髒資料污染個人帳本。

### 3.2 模組 G-02：全域標的治理與多因子排名 (Global Universe & Ranking Engine)

本模組落實**「月度狀態感知 (Monthly State Refresh) ＋ 半年度決策執行 (Semi-Annual Decision Execution)」**架構：
* **每月 15 日（配合證交所定期定額排行公告）**：系統自動刷新全市場標的分類（核心/衛星/債券/排除），並對新上市滿 30 個交易日（高斯中心極限定理 $N \ge 30$）之新標的執行「快速通道 (Fast-Track)」篩選，即時更新戰情室客觀候選池。
* **每半年（6/30 與 12/31 收盤後）**：正式鎖定多因子總排名，驅動個人投組層 (P-01, P-02) 進行 1.4N 緩衝換倉與工單求解，兼顧市場新陳代謝敏銳度與低交易摩擦。

#### 1. 三大資產層級硬約束過濾 (Hard Constraints)

| 資產層級 | 目標功能 | 納入硬約束條件 | 淘汰約束條件 |
| --- | --- | --- | --- |
| **核心大盤 (Core)** | 穩健 Beta 基石 | 1. 廣基指數（如 0050、006208、00646 等，走勢回歸 $R^2 \ge 0.90$）<br>2. 總費用率 $\text{TER} \le 0.45\%$<br>3. 規模 $\text{AUM} \ge 100$ 億 TWD<br>4. **【新大盤 30 交易日快速通道】**：新掛牌滿 $N \ge 30$ 個交易日，且 $R^2 \ge 0.95$、$\text{TER} \le 0.45\%$、$\vert{}\text{折溢價}\vert{} \le 0.5\%$、$\text{AUM} \ge 50$ 億（或登入定期定額 Top 20 排行）者，直接破格核准納入！ | 連續 2 季追蹤誤差 $> 1.2\%$ 或 AUM 跌破 30 億 TWD |
| **動能衛星 (Satellite)** | 獲取超額動能與收割波動 | 1. 高成長科技/關鍵資源/特定主題<br>2. 近 252 日（未滿者取實際掛牌天數，最低門檻**滿 60 交易日**）日均成交額 $> 2,000$ 萬 TWD<br>3. 滾動年化波動度 $\sigma \ge 18\%$<br>4. 與核心大盤相關係數 $\rho_{\text{core}} < 0.85$ | 跌破 200 EMA 超過 60 個交易日，或流動性持續萎縮 (日均量 $< 1,000$ 萬) |
| **防禦債券 (Defensive)** | 鎖定現金流與安全墊 | 1. 現券型投資級公司債或中天期公債（如 00720B、00725B）<br>2. 信用評等 $\ge \text{BBB}$ 級<br>3. 存續期間在 $8 \sim 14$ 年區間<br>4. **嚴禁任何每日重置槓桿倍數之產品（槓桿倍數嚴格 $= 1.0\times$）** | 發行機構系統性違約降級潮，或次級市場溢價 $> 1.5\%$ |

* **核心標的豁免條款**：核心大盤標的**永久禁止產生任何主動清倉指令**，僅接受資金流入與再平衡補償。

#### 2. 多因子客觀評分公式

* **核心大盤評分 ($S_{\text{core}}$)**：
  $$S_{\text{core}} = 0.35 \times \text{TER\_Score} + 0.25 \times \text{AUM\_Score} + 0.30 \times \text{TrackingError\_Score} + 0.10 \times \text{Spread\_Score}$$
* **動能衛星評分 ($S_{\text{sat}}$)**：
  $$S_{\text{sat}} = 0.30 \times \text{MOM} + 0.20 \times \text{Sharpe} + 0.20 \times \text{Hurst} - 0.15 \times \rho_{\text{core}} + 0.15 \times \text{DCARank\_Score}$$

  * $\text{DCARank\_Score}$：證交所定期定額戶數排行換算得分，代表市場強烈共識與散戶流動性支撐。

#### 3. 每日盤後停利告警與超跌加碼雷達 (整合日常巡檢習慣)
* **自適應波動度移動停利告警 (US-P02-03)**：
  * **標的適用範圍**：嚴格限定**動能衛星 (SATELLITE)** 標的；**核心大盤 (CORE) 永久豁免停利**（只進不出，維持終身長線複利底座）。
  * **硬約束前置門檻（量化停利鐵三角：規模、幅度、效率）**：
    1. **持有規模約束**：累積持有總股數必須滿 1 整張（$Q_{\text{current}} \ge 1,000$ 股）；未滿 1 張不發動停利，避免零股折價滑價與瑣碎小額交易。
    2. **絕對獲利規模約束 (MEAT 門檻)**：預估已實現獲利金額必須 $\ge \text{MEAT}$ (30,000 TWD)。
       * *量化反推依據*：在定期定額架構下（例如每月扣款 10,000 元，10 個月累積本金 10 萬元），由於分批買進均價隨漲幅持續墊高，標的需自起扣點爆發超過 30%~50% 實質大波段漲幅方能累積出 30,000 元淨利潤。此門檻能嚴格避開短線本金過小時虛胖的假停利，確保部位累積足夠本金厚度，停利出清整張時能一口氣釋出 13 萬以上大額現金，方具備實質再平衡之顯著規模。
    3. **資本效率約束 (Alpha Hurdle)**：該持倉之資金加權年化報酬率必須**超越標普 500 長線基準（$\text{XIRR} \ge 10.0\%$）**，確保收割的是真正的超額報酬（Alpha），跑輸大盤之平庸部位移交 G-02 多因子體檢汰除。
  * **自適應幅度雙指標（去常數化求解）**：
    * 動態停利啟動目標：$T_i = \text{Clamp}\left(0.75 \times \sigma_{252, i}, \; 10\%, \; 30\%\right)$。
    * 動態波段回撤門檻：$D_i = \text{Clamp}\left(0.30 \times \sigma_{252, i}, \; 5.0\%, \; 12.0\%\right)$（拒絕死板常數，依標的年化波動度自適應提供呼吸空間）。
    * 觸發條件：未實現報酬率曾達標 $T_i$，且當前收盤價相較於自達標以來的「波段最高價」累計回撤幅度 $\ge D_i$（確立動能竭盡與波段頭部確立）。
  * **賣出數量公式（整張出清、零股留種）**：
    $$\text{建議賣出股數 } Q_{\text{sell}} = \left\lfloor \frac{Q_{\text{current}}}{1000} \right\rfloor \times 1000 \quad (\text{100\% 純整張委託，零滑價秒速撮合})$$
    $$\text{帳戶留存股數 } Q_{\text{remain}} = Q_{\text{current}} \bmod 1000 \quad (\text{留作種子，維持券商約定定期定額合約無縫續扣})$$
  * 戰情室主動亮燈提醒，顯示預估釋出現金與獲利，**使用者只需在券商 App 執行 1 次純整張賣出**。
* **逢低超跌加碼雷達 (US-P02-04)**：
  * 每日比對核心大盤負乖離率（跌破 200 EMA 超過閥值）或波段回撤。
  * 偵測到超跌時主動提示：「*0050 自高點回撤達 -16.5%，建議單筆手動加碼 1 張，預估攤平成本至 168 元*」，引導動用交割戶停利沉澱現金手動撈底，兼顧紀律。

#### 4. 標的獨立扣款排程與現金流增量自動再平衡 (Decoupled DCA & Cash-Flow Rebalancing)
* **標的獨立排程**：各標的支援設定獨立扣款日 `dca_days`（如 0050 設 6 號、00646 設 16 號、00720B 設 26 號）與約定扣款金額。
* **免每月改定額**：日常由券商自動扣款，系統不頻繁調整約定定額；約定額度僅在**每半年審核 (6/30, 12/31)** 時重算推薦一次。
* **現金流增量自動再平衡 (Cash-Flow Driven Inflow Rebalancing - 預設主軌道)**：
  * 停利賣出整張所釋出的大額現金（本金 ＋ 利潤），於交割後回流至單一交割戶 (`Free Cash`)。
  * **核心哲學（均線回填免手動買單）**：系統**不強制要求使用者在停利當日手動下單即時買進核心**（避免大多頭高檔追高接刀與兩段式下單摩擦）。該筆閒置資金作為「定期定額燃料庫」，由原本約定好的核心大盤與防禦債券之定期定額排程（如 6, 16, 26 號）在未來數月內**平滑、分批、自動於均線均價買入核心**，達成真正優雅的夏農波動收割閉環。
* **低頻單筆工單觸發例外 (Manual Rebalancing Exceptions)**：
  1. 孤兒標的 (ORPHAN) 汰換清倉且釋出大額現金；
  2. 標的權重偏離目標超出容忍帶 $\vert{}\frac{W_{\text{actual}} - W^*}{W^*}\vert{} \ge 25\%$；
  3. 「逢低超跌加碼雷達」亮燈確認手動加碼。

#### 5. 先賣後買工單求解器與已實現資本利得記錄
* **先賣後買原則**：工單排序嚴格遵守「先出清 ORPHAN 與衛星停利賣單 $\to$ 確認交割款 $\to$ (若有) 執行買單」，杜絕違約交割。
* **整零股委託最佳化**：
  * **衛星停利單**：100% 嚴格為「整張委託（$\lfloor Q/1000 \rfloor$ 張）」，永不產生零股賣單。
  * **ORPHAN 出清單**：整張出清 ＋ 零股結清（徹底清空被淘汰標的）。
  * **超跌加碼買單**：優先建議「整張買進（1 張）」，免除零股撮合困擾。
* **已實現資本利得入帳**：
  * 使用者點擊「確認賣出成交」後，系統依加權平均成本自動結算：
    $$\text{已實現資本利得} = (\text{成交單價} - \text{買入均價}) \times \text{賣出股數} - \text{手續費} - \text{證券交易稅 (0.1\%)}$$
  * 寫入 `TradeTransaction` 交易流水帳，並自動累計至當月/年度已實現損益統計。

#### 6. 三大極簡 What-If 壓力沙盤推演
系統提供無副作用的虛擬推演：
* **劇本 A（大盤常態回撤 -10%）**：試算哪些衛星會觸發移動停利、核心大盤產生的權重缺口。
* **劇本 B（黑天鵝暴跌 -30%）**：預演防禦債券套現 50% 抄底核心大盤的確切股數與金額。
* **劇本 C（降息 100bps/景氣衰退）**：預演公司債 YTM 跌破 3.5% 觸發債券停利釋放的資本利得規模。

### 4.4 模組 P-04：個人月度對帳月報、退休導航與歸因 (Personal Hurdle & Ledger)

#### 1. 月度資產對帳月報 (全面取代 Excel 檔案)
* 每月自動生成資產淨值快照（股票現值 + 債券現值 + 現金）。
* 自動拆解當月淨值月增減金額 ($\Delta V$) 與月增減率 (MoM %)：
  $$\Delta V_{\text{total}} = \underbrace{\Delta C_{\text{savings}}}_{\text{本月新儲蓄注資}} + \underbrace{\Delta P_{\text{market}}}_{\text{市場資本利得/未實現損益}} + \underbrace{D_{\text{dividends}}}_{\text{已實現配息入帳}}$$
* 繪製個人長線資產累積走勢圖，徹底省去每個月開啟 Excel 鍵入對帳單的痛點。

#### 2. 退休目標 Hurdle Rate 與蒙地卡羅財富漏斗錐 (Cone of Wealth)
* **由上而下求解**：輸入退休剩餘年限 $T$、目前總資產 $V_0$ 與預期退休金終值 $V_{\text{target}}$，求解達標所需之最低實質年化報酬率 $r_{\text{req}}$。
* **蒙地卡羅推演**：模擬 10,000 次路徑，建立 $P_{10} \sim P_{90}$ 財富漏斗錐。
* **航道偏離狀態機 (Trajectory State)**：
  * `AHEAD` ($\text{Gap} \ge +20\%$)：超前預期，提示獲利鎖定。
  * `ON_TRACK` ($-10\% \le \text{Gap} < +20\%$)：維持紀律，無須調整。
  * `LAGGING` ($-25\% \le \text{Gap} < -10\%$)：計算需額外補貼之月儲蓄額 $\Delta C$。
  * `CRITICAL` ($\text{Gap} < -25\%$ 連續 2 季)：觸發策略重審會話，建議延後退休或調降終值。

#### 3. 雙重績效度量與三源績效歸因
* **Unitized TWR**：單元化時間加權報酬率，排除存提款干擾，對標大盤 Benchmark。
* **MWR / XIRR**：資金加權報酬率，真實反映個人帳戶年化複合成長率。
* **三源歸因模型**：
  $$\text{Total Return} = \beta \cdot R_{\text{market}} + \alpha_{\text{shannon}} + R_{\text{carry}}$$
  * 每日同步運算「靜態買入死抱到底 (Buy & Hold)」對照組，證明夏農收割超額 $\alpha_{\text{shannon}}$ 的真實價值。

  * 任何外部請求進入時，自動觸發冷啟動（Cold Start）提供服務。

#### 5.1.2 外部排程喚醒架構 (External Cloud Scheduler Orchestration)
* **痛點消除（解決實例為 0 與多實例競爭）**：
  * 在 Cloud Run 容器內部執行常駐定時器（如 `@Scheduled` 或 Linux Cron）存在兩大致命缺陷：(1) 實例縮容至 0 時定時器直接停擺；(2) 流量高峰觸發多實例並行擴展時，多個容器同時執行排程將造成嚴重的資料重複拉取與寫入競爭（Race Condition）。
  * 系統採取「**排程邏輯與運算執行完全解耦**」原則：容器內部不維護常態性時間定時器，改由 **GCP Cloud Scheduler** 承擔外部統一排程器角色。
* **觸發機制與排程配置**：
  * 頻率：每日台北時間 08:00 (UTC 00:00，Cron: `0 0 * * 1-5`)。
  * 目標端點：`POST https://<CLOUD_RUN_SERVICE_URL>/api/v1/jobs/sync-market-data`。
  * 任務職責：喚醒 Cloud Run 單一實例，依序執行 G-01 市場資料拉取、守門員檢核、G-02 多因子評估與 G-03 宏觀利率狀態機更新。

#### 5.1.3 雙軌身分認證閘門架構 (Dual-Ingress Authentication: IAP & OIDC Coexistence)
打破傳統「IAP 網頁驗證與 IAM 服務叫用只能二選一」的迷思，系統建構業界標準的**雙軌身份共存架構**：

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        雙軌流量進入閘門 (IAP & OIDC Ingress Architecture)               │
├────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                        │
│  【人類使用者通道：Web 瀏覽器】                                                         │
│   使用者發起請求 (GET /)                                                               │
│          │                                                                             │
│          ▼                                                                             │
│  ┌──────────────────────────────────────────────┐                                      │
│  │ Google Cloud IAP (Identity-Aware Proxy) 邊界 │ ◄── 轉址 Google OAuth 網頁登入         │
│  └──────────────────────┬───────────────────────┘     檢查 roles/iap.httpsResourceAccessor │
│                         │ 通過驗證                                                      │
│                         ▼ 注入 Header: X-Goog-Authenticated-User-Email                 │
│  ┌──────────────────────────────────────────────────────────────────────────────────┐  │
│  │ Cloud Run 容器應用程式 (Spring Boot)                                              │  │
│  │  - 個人投組層 (P-01 ~ P-04)：依 User Email 嚴格隔離多租戶個人資產帳本            │  │
│  └──────────────────────────────────────────────────────────────────────────────────┘  │
│                         ▲                                                              │
│                         │ 通過驗證                                                      │
│  ┌──────────────────────┴───────────────────────┐                                      │
│  │ Google Cloud IAP (Identity-Aware Proxy) 邊界 │ ◄── 驗證 OIDC Bearer Token            │
│  └──────────────────────────────────────────────┘     Audience = IAP OAuth Client ID   │
│          ▲                                            檢查 roles/iap.httpsResourceAccessor │
│          │ 攜帶 OIDC ID Token (由專屬 Service Account 簽署)                            │
│  【自動排程通道：GCP Cloud Scheduler】                                                 │
│   每日定時觸發 POST /api/v1/jobs/sync-market-data                                      │
│                                                                                        │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

* **軌道一：人類 Web 使用者通道 (End-User Browser Channel)**：
  1. 存取點：瀏覽器存取 Cloud Run 服務網址或綁定網域。
  2. 認證流程：由 Google Cloud IAP 自動攔截未登入連線，導向 Google OAuth 登入介面，強制檢查使用者是否具備 `roles/iap.httpsResourceAccessor` 存取授權。
  3. 帳本隔離：IAP 驗證放行後，自動向後端注入 `X-Goog-Authenticated-User-Email` 與 `X-Goog-IAP-JWT-Assertion` Header。後端個人投組層（P-01 ~ P-04）以此 Email 作為唯一租戶 Key，達成多租戶資產與庫存的物理級數據隔離。
* **軌道二：自動化排程機器人通道 (Cloud Scheduler Service Account Channel)**：
  1. 存取點：Cloud Scheduler HTTP Target，指向 `/api/v1/jobs/sync-market-data`。
  2. 專屬身分：指派專用 Service Account（如 `alpha-harvester-scheduler@${PROJECT_ID}.iam.gserviceaccount.com`）。
  3. **Audience 規格規範（防 401 關鍵約束）**：
     * 啟動 IAP 後，Cloud Scheduler 的 `--oidc-token-audience` **必須嚴格填入該 IAP 背後綁定的「OAuth 2.0 Client ID」**（格式為 `*.apps.googleusercontent.com`），而非 Cloud Run 服務網址！
  4. **IAM 雙重授權綁定**：該 Service Account 必須同時被授予：
     * `roles/run.invoker`（Cloud Run 叫用權限）
     * `roles/iap.httpsResourceAccessor`（穿越 IAP 閘道存取權限）

#### 5.1.4 應用層深度防禦 (Application-Level Defense-in-Depth)
* **維運排程端點防護**：
  * 後端在 `/api/v1/jobs/**` 路由實施二次權限白名單過濾。
  * 即使一般合法使用者登入 IAP，若其 Email 不在核准的 Scheduler Service Account 清單內，後端直接拒絕並回傳 `403 Forbidden`，防止一般終端使用者惡意或誤觸重度數據採集管線。

#### 5.1.5 持久化儲存與資料分區 (Persistence & Tenant Isolation)
* **雲端資料庫**：採用雲端託管關聯式資料庫 (Cloud SQL PostgreSQL / SQLite 雲端持久掛載)。
* **全域 vs 個人分區**：
  * 全域市場行情與宏觀狀態資料表為全系統共享，不帶租戶 ID。
  * 所有個人持倉、扣款日曆、交易流水與對帳月報均以 `user_email` 進行嚴格外鍵約束與索引分區。

### 5.2 介面體驗與小白友善規格 (Beginner-Friendly UX)
* **四步月度引導流程**：
  1. *查看市場與宏觀狀態*（系統自動顯示高利蓄水/常態平衡等綠燈）。
  2. *輸入交割戶可用現金*（小白每月只要填一個數字）。
  3. *查看工單建議*（清楚標示整股幾張、零股幾股、預估成交金額）。
  4. *下單完成後一鍵確認*。
* **全平台 Web 介面響應式設計**：支援桌面瀏覽器與手機瀏覽器自適應呈現。
* **零外部檔案依賴**：不提供 PDF/JSON 匯出，所有數據與圖表即時於線上戰情室渲染。
